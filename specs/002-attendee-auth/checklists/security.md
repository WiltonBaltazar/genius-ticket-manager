# Security & Auth-Flow Requirements Checklist: Attendee Authentication

**Purpose**: Formal, sign-off-quality review of the security and auth-flow requirements across spec.md, plan.md, research.md, data-model.md, and contracts/auth-api.md — the first feature in this project handling passwords, sessions, and account security. Author self-check, formal-gate depth, before `/speckit-tasks`.
**Created**: 2026-08-03
**Feature**: [spec.md](../spec.md)

**Note**: This checklist tests the requirements themselves, not any implementation. Items are questions about what is/isn't written, not verification steps.

## Requirement Completeness

- [x] CHK001 Does any requirement state that passwords MUST be stored hashed and never in plaintext, or is this left entirely to an implementation-detail mention in plan.md/research.md? [Gap, Spec §FR-003] — Resolved: new FR-024 states passwords MUST be irreversibly hashed and never appear in logs/audit/errors; data-model.md's attendees section cross-references it.
- [x] CHK002 Is registration itself rate-limited, or can the `/register` endpoint be called an unlimited number of times per origin? [Gap] — login (FR-012) and password reset (FR-017) are both throttled; registration has no stated limit, despite being a vector for mail-queue flooding and claim/reject-response account enumeration at volume. — Resolved: FR-023 added (5/min per IP), task T015 throttled, T012 tests the 429 case.
- [x] CHK003 Does any requirement address whether a logged-in attendee can change their password while authenticated (distinct from the forgot-password flow), or is this explicitly out of scope? [Gap, Spec §User Story 3] — Resolved: new Assumption states authenticated password change is a distinct, out-of-scope capability for this feature.
- [x] CHK004 Is multi-factor authentication explicitly declared out of scope, or simply unaddressed? [Gap, Spec §Assumptions] — Resolved: new Assumption explicitly states MFA is out of scope; login is single-factor only.
- [x] CHK005 Does FR-020 ("invalidate all of an attendee's existing sessions" on password reset) address the `remember_token` column, or only session-store rows? [Gap, Spec §FR-020, data-model.md §attendees] — a valid "remember me" cookie could otherwise out-live a session invalidation. — Resolved: FR-020 reworded to include remember-me credentials; task T027 cycles `remember_token` on reset.
- [x] CHK006 Is there a requirement that the IP address used for login throttling (FR-012) and audit logging (FR-013/FR-014) reflects the actual client, resistant to trivial spoofing via forwarded-for headers on a proxied deployment? [Gap, Spec §FR-012] — Addressed at the task level: T038 configures trusted proxies. No dedicated FR was added (judged to be a deployment-configuration concern, not a business requirement) — revisit if that judgment call is wrong.
- [x] CHK007 Is there a requirement that failed-login audit entries (FR-014) never capture the submitted password or reset token in any field, including free-text/diagnostic ones? [Gap, data-model.md §audit_logs] — Resolved: FR-014 amended with an explicit never-log-credentials clause; data-model.md's audit_logs section restates it against the fixed `changes` shape; T018 tests it.
- [x] CHK008 Is a maximum password length specified, given the chosen hashing algorithm's own input-length behavior is a real constraint independent of the minimum-strength policy? [Gap, Spec §FR-003] — Resolved: FR-003 now states a 12–72 character range (72 = bcrypt's input limit); T013/T026 add `max:72`; T012 tests the over-length case.
- [x] CHK009 Does any requirement address session-fixation prevention (issuing a fresh session identifier upon successful authentication, not upon initial page load)? [Gap, Spec §FR-011] — Resolved: new FR-025 requires session regeneration on login; T020 already implemented this, T018 now explicitly asserts the session ID changes.

## Requirement Clarity

- [x] CHK010 Is "a reasonable rate limit" for verification resend (FR-007) quantified anywhere, or does it remain a qualitative phrase resolved only in an Assumption? [Clarity, Spec §FR-007 vs §Assumptions] — Resolved: FR-007 now states "one resend per minute per origin" directly, matching the figure that was previously only in Assumptions.
- [x] CHK011 Is "deliverable domain (valid mail-exchange record)" (FR-002) precise enough to know whether a domain with no MX record but a valid A/AAAA record (implicit MX per RFC 5321) is accepted or rejected? [Clarity, Spec §FR-002] — Resolved: FR-002 reworded to explicitly accept the RFC 5321 implicit-MX (A/AAAA) fallback; T012/T013 note Laravel's `dns` rule already implements this with no custom code needed.
- [x] CHK012 Is "originating network address" (FR-013) defined precisely enough to know whether it means the immediate TCP peer or a forwarded client address? [Clarity, Spec §FR-013] — same underlying question as CHK006, from the wording side rather than the security-gap side. — Resolved: FR-013 now parenthetically clarifies it's the resolved client address (post trusted-proxy handling, per FR-012/T038), not necessarily the immediate TCP peer.

## Requirement Consistency

- [x] CHK013 Are the login-failure response categories (generic invalid-credentials vs. distinct unverified-email) consistently described the same way across spec.md's FR-009/FR-010 and contracts/auth-api.md's `422`/`423` definitions? [Consistency, Spec §FR-009 vs contracts/auth-api.md] — Verified consistent: contract's `422`/`423` responses directly implement FR-009/FR-010's language with no drift; no edit needed.
- [x] CHK014 Is the password strength policy (FR-003) stated identically everywhere it's referenced (FR-017, contracts/auth-api.md's `/register` and `/reset-password`), with no drift in the specific character-class requirements? [Consistency, Spec §FR-003, §FR-017] — Verified consistent: FR-019 (not FR-017) cross-references FR-003 by ID rather than restating specifics, and both contract endpoints just say "meets strength policy" — single source of truth, no drift possible. No edit needed.
- [x] CHK015 Does data-model.md's claim-vs-reject resolution (an existing passwordless row is updated, not replaced) preserve the Attendee's original `id` and prior `orders` relationship, and is that continuity explicitly stated rather than assumed? [Consistency, data-model.md §attendees, Spec §FR-005] — Resolved: data-model.md's attendees section now explicitly states the `id` never changes and the `orders` relationship is preserved automatically since the row is updated in place, not replaced.

## Acceptance Criteria Quality

- [x] CHK016 Can SC-003's "100% of successful logins and 100% of failed login attempts each produce exactly one corresponding audit record" be verified given research.md §6's own carve-out that failed attempts against nonexistent emails are *not* audited? [Conflict, Spec §SC-003 vs research.md §6] — Resolved: SC-003 reworded to qualify "against identifiable accounts" and explicitly names the IP-throttle carve-out.
- [x] CHK017 Is SC-005 (IP login-throttle) measurable without the specific rate (5/minute) being stated in spec.md itself, or only in research.md/plan.md? [Gap, Spec §SC-005] — Resolved: FR-012 now states "5 attempts per minute" directly, and SC-005 references the same figure.
- [x] CHK018 Is SC-006's "under 2 minutes" registration completion time measured from form-load or from first keystroke, and does it include time spent on the mail client checking for the verification email? [Ambiguity, Spec §SC-006] — Resolved: SC-006 reworded to specify "from first keystroke... to the in-app confirmation screen," explicitly excluding time in the attendee's own mail client.

## Scenario Coverage

- [x] CHK019 Is a recovery path defined for an attendee who has lost access to the email address on their account entirely (cannot receive verification or reset emails), or is this explicitly out of scope? [Gap, Recovery Flow] — Resolved: new Assumption states this is out of scope; email is the sole recovery channel this feature provides.
- [x] CHK020 Are requirements defined for an attendee attempting to register or reset a password while an active, valid session already exists for that same account? [Gap, Alternate Flow] — Resolved: new edge case + Assumption — handled by frontend route redirection, not special backend logic, since the endpoints remain valid to call regardless of the caller's session state.
- [x] CHK021 Are requirements defined for concurrent password-reset requests for the same account (two valid, unexpired reset tokens outstanding at once) — does completing one invalidate the other? [Gap, Edge Case] — Resolved: data-model.md now explains `password_reset_tokens.email` being the primary key means at most one token can exist per address; a second request overwrites the first, and no separate invalidation logic is needed. T024 now tests this.

## Edge Case Coverage

- [x] CHK022 Is the resend-verification behavior specified for an email that has no matching account at all, consistent with the enumeration-avoidance stance already taken for `/forgot-password`? [Gap, contracts/auth-api.md §/email/verification-notification] — Resolved: FR-007 and contracts/auth-api.md both now explicitly state the response is identical across unverified, already-verified, and nonexistent-email cases.
- [x] CHK023 Are requirements defined for a registration attempt where the claimed guest-checkout record (FR-005) has a different `name` on file than the one submitted at registration — does the submitted name overwrite it, or is the original preserved? [Gap, data-model.md §attendees] — Already resolved (pre-existing): data-model.md's claim-vs-reject rule already stated "overwrite `name`/`phone` with the submitted values" — confirmed unambiguous on review, no edit needed.
- [x] CHK024 Is behavior defined for a password-reset attempt using a token whose account was soft-deleted (feature 001 erasure) between the reset request and its completion? [Gap, Edge Case] — Resolved: new edge case + data-model.md note — the broker's default soft-delete-respecting lookup fails the same way an invalid token would, no special-case code needed. T024 now tests this.

## Non-Functional Requirements

- [x] CHK025 Are transport-security requirements (HTTPS-only cookies, `Secure`/`HttpOnly`/`SameSite` session-cookie attributes) stated anywhere, or left entirely to the constitution's general "HTTPS MUST be enforced" principle without auth-specific reinforcement? [Gap, Non-Functional] — Resolved: new FR-026 requires these cookie attributes explicitly; new task T039 sets `SESSION_SECURE_COOKIE=true` for non-local environments and confirms the other two Laravel defaults already satisfy it.
- [x] CHK026 Is there a stated requirement for how long failed-login audit records (FR-014) are retained, consistent with feature 001's unresolved retention question for `audit_logs` generally? [Gap, Non-Functional] — Intentionally not resolved here: this is feature 001's general, still-open `audit_logs` retention question (not specific to failed-login rows), and duplicating a partial answer in this feature's spec would fragment that decision across two specs. Deferred to wherever feature 001's retention question is eventually answered.

## Dependencies & Assumptions

- [x] CHK027 Is the dependency on DNS/MX lookups being available and performant from the shared-hosting environment (FR-002) validated anywhere, given constitution Principle VI's shared-hosting constraints? [Assumption, Spec §FR-002] — Resolved: new Assumption acknowledges this as a standard PHP capability worth confirming at deployment, rather than silently assumed.
- [x] CHK028 Is the assumption that Laravel's default mail queue (`database` driver, per feature 001) can absorb verification/reset email volume without a dedicated worker cross-checked against constitution Principle VI's "no persistent workers" constraint? [Assumption, plan.md vs constitution.md Principle VI] — Resolved: new Assumption states verification/reset emails are processed by the same once-a-minute cron-triggered scheduler that already drains the queue for other work — no new infrastructure, consistent with Principle VI.

## Ambiguities & Conflicts

- [x] CHK029 Does FR-010 ("MUST NOT reveal... whether a given email address has a registered account when the failure is due to incorrect credentials") fully align with FR-004's registration-time disclosure that an email is already taken — is the boundary between these two intentionally-different disclosure postures stated explicitly, or does a reader have to infer it? [Consistency, Spec §FR-004 vs §FR-010] — Resolved: the Assumptions entry on the `423` tradeoff was expanded into a full three-way explanation distinguishing FR-004 (registration disclosure), FR-009 (unverified-login disclosure), and FR-010 (incorrect-credentials non-disclosure) as independently-justified decisions, not one blanket policy.
- [x] CHK030 Is it explicit that the `423` unverified-email response (FR-009) is itself a form of account-existence disclosure (distinct from FR-010's protection against credential-validity disclosure), and that this is an accepted, deliberate tradeoff rather than an oversight? [Ambiguity, Spec §FR-009 vs §Assumptions] — Resolved by the same expanded Assumptions entry as CHK029.
